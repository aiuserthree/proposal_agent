# consensus-builder

## 1. 목적과 컨텍스트

에이전트 산출물 간 **주장 충돌·수치 불일치·범위 해석 차이**를 한 문서로 정리하고, **합의안·미합의·후속 조치**를 명시한다. `collaboration-protocol`의 합의 절차와 연동된다.

## 2. 입력 명세

| 구분 | 항목 | 필수 |
|------|------|------|
| 필수 | 충돌 이슈 목록(파일명·절·내용 요약) | 예 |
| 필수 | 관련 RFP·rfp-analysis 인용 | 예 |
| 선택 | critic-review 의견 | 권장 |
| 선택 | 우선순위 규칙(RFP>데이터>추론) | 아니오 |

## 3. 출력 명세

| 항목 | 내용 |
|------|------|
| 경로 | `workspace/discussions/consensus-{YYYY-MM-DD}.md` |
| 형식 | 이슈별 표 + 결론 + 책임자(에이전트 역할) |

## 4. 단계별 실행 절차 (5단계)

1. **수집**: 각 draft에서 상충하는 문장·수치를 추출한다.
2. **분류**: 사실 문제 vs 해석 문제 vs 범위 문제로 나눈다.
3. **근거 매칭**: RFP 원문, analyst 데이터, 외부 출처 우선순위를 적용한다.
4. **결론**: 합의안 문장을 확정하거나 옵션 A/B로 분기한다.
5. **저장**: consensus 파일에 반영하고 재작성 대상 에이전트를 지정한다.

## 5. 품질 기준

1. 모든 열린 이슈에 **상태**(합의/보류/옵션)가 있음.
2. 보류 시 **담당자·다음 액션**이 명시됨.
3. RFP 근거가 있으면 REQ ID를 병기.
4. 합의 문장은 최종 제안서에 직접 붙여넣을 수 있을 정도로 명확.
5. 3회 이상 미해결 시 Orchestrator 에스컬레이션 플래그.

## 6. 출력 템플릿

```markdown
# 합의 기록 YYYY-MM-DD

## 이슈 요약
| ID | 충돌 내용 | 관련 파일 | 우선 근거 |
|----|-----------|-------------|-----------|
| C-01 | | | |

## 결론
### C-01
- **결정**:
- **반영 위치**: PART / 절
```

## 7. 에러 처리 규칙

| 상황 | 처리 |
|------|------|
| 근거 부족 | "미확정" + 사용자 확인 요청 |
| RFP 모호 | 옵션 A/B + 리스크 설명 |

## 8. 연계 스킬·에이전트

| 연계 대상 | 용도 |
|-----------|------|
| proposal-factory 규칙 | writing-style, proposal-structure, output-format 준수 |
| Orchestrator | 단계 산출물 승인·재작성 루프 |
| Critic | 일관성·RFP 대응 재검토 |

## 9. 관련 규칙 파일

- `rules/writing-style.mdc` — 분량·톤·금지어
- `rules/proposal-structure.mdc` — PART 배치
- `rules/collaboration-protocol.mdc` — 저장 경로·합의
- `rules/output-format.mdc` — Markdown·Mermaid

## 10. 품질 자가점검 체크리스트

- [ ] 입력 명세의 필수 항목이 모두 충족되었는가?
- [ ] 출력 경로·파일명이 collaboration-protocol과 일치하는가?
- [ ] 표·절 번호가 최종 제안서에서 참조 가능한가?
- [ ] 금지 표현(writing-style)이 제거되었는가?
- [ ] 에러/예외 시나리오가 문서화되었는가?

## 11. 산출물 보존·재실행

- 동일 날짜 재실행 시 파일명에 `_v2` 또는 시각 접미를 붙인다.
- 중간 산출물은 삭제하지 않고 보관하여 critic 재검토에 대비한다.
- MCP 실패 시 대체 경로(web_search 등)를 보고서에 명시한다.

## 12. 용어·메타데이터

- 문서 상단에 `generated_for`, `rfp_ref`, `skill_version: 1` 메타를 주석으로 남길 수 있다.
- 고객사 고유명사는 RFP 표기를 그대로 사용한다.


## 13. 상세 실행 노트 (공통)

1. 스킬 실행 전 `workspace/discussions/rfp-analysis.md` 존재 여부를 확인한다.
2. 산출물은 UTF-8(LF)로 저장하고, 표·코드블록 들여쓰기를 유지한다.
3. 수치·날짜는 writing-style의 숫자 표기 규칙을 따른다.
4. 본 스킬 산출물을 인용하는 최종 PART는 proposal-structure의 해당 절을 명시한다.
5. 재현성을 위해 사용한 검색어·URL·도구명을 부록 또는 각주에 남긴다.

## 14. 한계 및 면책

- 공개되지 않은 정보는 추론·가정으로 표시하며, 계약·법적 효력이 있는 수치는 발주처 확인을 전제로 한다.
- MCP·외부 API 장애 시 결과 파일 상단에 장애 요약을 기록한다.
