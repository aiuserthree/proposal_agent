# reference-matcher

## 1. 목적과 컨텍스트

`references/index.md`에 등록된 **과거 제안서·샘플** 중 현재 과제와 유사한 문서를 선별한다. 문체·목차·실적 예시를 재사용할 근거를 제공하며, **원문 복제**가 아닌 **구조·표현 참고** 용도로 한정한다.

## 2. 입력 명세

| 구분 | 항목 | 필수 |
|------|------|------|
| 필수 | `rfp-analysis.md` 또는 동등 요약(사업 유형·산업·키워드) | 예 |
| 필수 | `references/index.md` 존재 | 예 |
| 선택 | 가중치 오버라이드(유형 40% 기본) | 아니오 |

## 3. 출력 명세

| 항목 | 내용 |
|------|------|
| 경로 | `workspace/discussions/reference-match-{YYYY-MM-DD}.md` |
| 형식 | Markdown — 순위별 레퍼런스, 점수 근거, 인용 가능 범위 |

## 4. 단계별 실행 절차 (6단계)

1. **인덱스 로드**: `references/index.md`에서 후보 목록과 태그를 읽는다.
2. **특징 벡터**: 현재 RFP에서 유형·산업·키워드·규모(예산/기간)를 추출한다.
3. **가중 스코어**: 유형 40%, 산업 30%, 키워드 20%, 규모 10%로 유사도를 계산한다.
4. **랭킹**: 상위 1~3순위를 선정하고 동점 시 최신·완성도 우선.
5. **근거 기록**: 각 순위에 왜 선택했는지 2~3문장으로 남긴다.
6. **저장**: `reference-match-{날짜}.md`에 결과를 저장한다.

## 5. 품질 기준

1. 선정 근거가 **정량 가중치**로 설명 가능할 것.
2. 상위 3개 이내로 제한하여 집중도 유지.
3. 고객사 기밀·저작권이 있는 문서는 **참고만** 명시.
4. RFP와 산업이 다르면 "참고 제한" 주석.
5. 매칭 실패 시 "후보 없음"을 명시하고 일반 목차만 사용.

## 6. 출력 템플릿

```markdown
# 레퍼런스 매칭 결과
- **기준일**: YYYY-MM-DD
- **현재 과제 요약**:

## 순위별 결과
### 1순위: [문서명]
- **점수**: 
- **근거**:
- **인용 가능 범위**: 목차 / 표현 / 실적

### 2순위: ...
```

## 7. 에러 처리 규칙

| 상황 | 처리 |
|------|------|
| index.md 없음 | 스킬 스킵, orchestrator에 보고 |
| 후보 0건 | 템플릿에 "매칭 없음", 제안서는 proposal-structure 기본만 |
| 태그 불일치 | 키워드 부분 일치로 완화 후 근거에 불확실성 표기 |

## 8. 연계 스킬·에이전트

| 연계 대상 | 용도 |
|-----------|------|
| proposal-factory 규칙 | writing-style, proposal-structure, output-format 준수 |
| Orchestrator | 단계 산출물 승인·재작성 루프 |
| Critic | 일관성·RFP 대응 재검토 |

## 9. 관련 규칙 파일

- `rules/writing-style.mdc` — 분량·톤·금지어
- `rules/proposal-structure.mdc` — PART 배치
- `rules/collaboration-protocol.mdc` — 저장 경로·합의
- `rules/output-format.mdc` — Markdown·Mermaid

## 10. 품질 자가점검 체크리스트

- [ ] 입력 명세의 필수 항목이 모두 충족되었는가?
- [ ] 출력 경로·파일명이 collaboration-protocol과 일치하는가?
- [ ] 표·절 번호가 최종 제안서에서 참조 가능한가?
- [ ] 금지 표현(writing-style)이 제거되었는가?
- [ ] 에러/예외 시나리오가 문서화되었는가?

## 11. 산출물 보존·재실행

- 동일 날짜 재실행 시 파일명에 `_v2` 또는 시각 접미를 붙인다.
- 중간 산출물은 삭제하지 않고 보관하여 critic 재검토에 대비한다.
- MCP 실패 시 대체 경로(web_search 등)를 보고서에 명시한다.

## 12. 용어·메타데이터

- 문서 상단에 `generated_for`, `rfp_ref`, `skill_version: 1` 메타를 주석으로 남길 수 있다.
- 고객사 고유명사는 RFP 표기를 그대로 사용한다.


## 13. 상세 실행 노트 (공통)

1. 스킬 실행 전 `workspace/discussions/rfp-analysis.md` 존재 여부를 확인한다.
2. 산출물은 UTF-8(LF)로 저장하고, 표·코드블록 들여쓰기를 유지한다.
3. 수치·날짜는 writing-style의 숫자 표기 규칙을 따른다.
4. 본 스킬 산출물을 인용하는 최종 PART는 proposal-structure의 해당 절을 명시한다.
5. 재현성을 위해 사용한 검색어·URL·도구명을 부록 또는 각주에 남긴다.

## 14. 한계 및 면책

- 공개되지 않은 정보는 추론·가정으로 표시하며, 계약·법적 효력이 있는 수치는 발주처 확인을 전제로 한다.
- MCP·외부 API 장애 시 결과 파일 상단에 장애 요약을 기록한다.
