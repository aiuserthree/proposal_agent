# rfp-parser

## 1. 목적과 컨텍스트

RFP·이메일·메모 등 **비정형 입력**을 제안서 파이프라인이 소비 가능한 **구조화 메타데이터**로 변환한다. `input-flexibility` Level 1~3에 대응하며, 후속 `rfp-compliance-checker`·Orchestrator의 기준 문서가 된다.

## 2. 입력 명세

| 구분 | 항목 | 필수 |
|------|------|------|
| 필수 | 원문 텍스트 또는 파일 경로 | 예 |
| 필수 | 작성 기준일(오늘 날짜) | 예 |
| 선택 | 발주처 공식 명칭·사업명 | 아니오 |
| 선택 | 첨부 목록·버전 | 아니오 |
| 선택 | project_type 힌트(A~E) | 아니오 |

## 3. 출력 명세

| 항목 | 내용 |
|------|------|
| 경로 | `workspace/discussions/rfp-analysis.md` (프로젝트 루트 `workspace/` 기준) |
| 형식 | Markdown, 섹션 고정 헤딩(아래 템플릿) |
| 부가 | REQ ID 목록, 평가기준 원문 인용, 제약·제출일 |

## 4. 단계별 실행 절차 (7단계)

1. **수집**: 입력 원문 전체를 확보하고 인코딩(UTF-8)을 맞춘다.
2. **분류**: `input-flexibility`에 따라 Level 1~3을 태그한다.
3. **추출**: 사업명, 발주처, 배경, 목적, 범위, 요구사항, 기술요건, 평가기준, 예산, 기간, 제출일, 제약을 필드별로 채운다.
4. **식별자**: 요구사항에 REQ-001… ID를 부여한다(RFP 원문 번호가 있으면 유지).
5. **갭 표시**: 빈 필드는 `N/A` 또는 `[추론]`으로 표기한다.
6. **검증**: 날짜·단위·모순(기간 vs 마일스톤)을 1차 점검한다.
7. **저장**: `rfp-analysis.md`에 쓰고 한 줄 요약을 discussions 로그에 남긴다.

## 5. 품질 기준 (5개 이상)

1. 필수 필드 누락 없음 또는 명시적 N/A.
2. REQ ID와 본문 인용문이 추적 가능하게 대응.
3. 평가기준이 있으면 **배점·항목명**을 왜곡 없이 기록.
4. Level 2~3에서 추론 항목은 `[추론]` 태그.
5. 고객사 공식 명칭·사업명 오타 최소화(의심 시 질문 리스트에 추가).

## 6. 출력 템플릿 (마크다운 예시)

```markdown
# RFP 분석 메타데이터
- **Level**: 1 | 2 | 3
- **사업명**:
- **발주처**:
- **제출일**:
- **작성일**:

## 1. 배경·목적
## 2. 범위(In/Out)
## 3. 요구사항 목록
| REQ ID | 원문 요약 | 비고 |
|--------|-----------|------|
| REQ-001 | | |

## 4. 기술 요건
## 5. 평가 기준
## 6. 예산·기간·제약
## 7. 미확인·추론 사항
```

## 7. 에러 처리 규칙

| 상황 | 처리 |
|------|------|
| 파일 읽기 실패 | 사용자에게 경로·권한 확인 요청, 텍스트 붙여넣기 폴백 |
| OCR 품질 저하 | 불확실 구간을 인용부호로 표시, 질문 리스트에 등록 |
| 요구사항 단편만 존재 | REQ 묶음을 주제별로 임시 그룹화하고 주석 명시 |
| 상충하는 두 버전 | 최신 제출본 우선, 차이는 표로 부록 |

## 8. 연계 스킬·에이전트

| 연계 대상 | 용도 |
|-----------|------|
| proposal-factory 규칙 | writing-style, proposal-structure, output-format 준수 |
| Orchestrator | 단계 산출물 승인·재작성 루프 |
| Critic | 일관성·RFP 대응 재검토 |

## 9. 관련 규칙 파일

- `rules/writing-style.mdc` — 분량·톤·금지어
- `rules/proposal-structure.mdc` — PART 배치
- `rules/collaboration-protocol.mdc` — 저장 경로·합의
- `rules/output-format.mdc` — Markdown·Mermaid

## 10. 품질 자가점검 체크리스트

- [ ] 입력 명세의 필수 항목이 모두 충족되었는가?
- [ ] 출력 경로·파일명이 collaboration-protocol과 일치하는가?
- [ ] 표·절 번호가 최종 제안서에서 참조 가능한가?
- [ ] 금지 표현(writing-style)이 제거되었는가?
- [ ] 에러/예외 시나리오가 문서화되었는가?

## 11. 산출물 보존·재실행

- 동일 날짜 재실행 시 파일명에 `_v2` 또는 시각 접미를 붙인다.
- 중간 산출물은 삭제하지 않고 보관하여 critic 재검토에 대비한다.
- MCP 실패 시 대체 경로(web_search 등)를 보고서에 명시한다.

## 12. 용어·메타데이터

- 문서 상단에 `generated_for`, `rfp_ref`, `skill_version: 1` 메타를 주석으로 남길 수 있다.
- 고객사 고유명사는 RFP 표기를 그대로 사용한다.


## 13. 상세 실행 노트 (공통)

1. 스킬 실행 전 `workspace/discussions/rfp-analysis.md` 존재 여부를 확인한다.
2. 산출물은 UTF-8(LF)로 저장하고, 표·코드블록 들여쓰기를 유지한다.
3. 수치·날짜는 writing-style의 숫자 표기 규칙을 따른다.
4. 본 스킬 산출물을 인용하는 최종 PART는 proposal-structure의 해당 절을 명시한다.
5. 재현성을 위해 사용한 검색어·URL·도구명을 부록 또는 각주에 남긴다.

## 14. 한계 및 면책

- 공개되지 않은 정보는 추론·가정으로 표시하며, 계약·법적 효력이 있는 수치는 발주처 확인을 전제로 한다.
- MCP·외부 API 장애 시 결과 파일 상단에 장애 요약을 기록한다.
